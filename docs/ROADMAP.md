# Roadmap

Ordered by prerequisite dependency. Each item lists its acceptance check.

## Done
- Boot, serial, GDT/IDT, PIC/PIT, PS/2 keyboard (pre-existing; the original BIOS/VGA text boot was replaced in M1 by UEFI boot and the framebuffer console).
- **Stage A terminal**: ISR-light input path, line editor, parser, shell commands. Verified by tests and `scripts/qemu_shell_smoke.py`.
- **Stage B (first pass)**:
  1. Exception handlers (#DE #UD #TS #NP #SS #GP #PF) with integration tests through the real IDT.
  2. Frame allocator, paging access, kernel heap (`tests/memory.rs`).
  3. Host-testable `l_core` crate (`scripts/host_tests.sh`).
  4. User mode: ring 3, `int 0x80`, per-process capability bits, pointer validation, time budget (`tests/usermode.rs`).
  5. Default-deny `NetPolicy` consulted by `SYS_NET_CHECK` (allow, deny, revoke, expiry tests).

- **Phase 0** (see PLAN_NEXT.md): CI, remaining exception handlers, panic path without lock, unwrap inventory.
- **Phase 1**: frame free list, per-process address spaces, process table, preemptive scheduler, SMEP/SMAP, pointer/stack-overflow tests.
- **Phase 2.1-2.3**: capability handles, delegation with attenuation, blocking IPC with deadlock cleanup.

- **Phase 2.4/2.5**: user-space build pipeline (`user/`, `build.rs`, validated ELF loader), `spawn`/`wait`, keyboard/system/spawner handles, shell in ring 3. (Deviation from the plan: console and keyboard are kernel objects reachable through handles, not separate service processes.)

- **Phase 3**: PCI, virtio-net, smoltcp, DNS client, policy at the syscall edge, socket handles, `net` shell commands (docs/NETWORK.md).
- **Phase 4**: hardware RNG, RTC, TLS 1.3 client (`l_tls`), `fetch`.

- **M1 Aurora framebuffer terminal** (spec `docs/superpowers/specs/2026-10-12-zukunftsplan-design.md`). Each claim names its test or script:
  - Pure `l_core` modules, host-tested by `scripts/host_tests.sh`: `cell`, `font` (Terminus 4.49.1 `ter-u16n`, OFL, generated by `scripts/gen_font.py`), `theme` (`AURORA`, contrast tests), `render` (grid to pixels, pinned by a golden hash), `widgets` (`rounded_box`, `HintBar` with at most 3 hints, `status_bar`), `anim` (`ease_out_cubic`, `blend`, `Fade`, `fade_theme`).
  - Boot via `bootloader` 0.11.17 + UEFI/OVMF with an own runner (`scripts/qemu_runner.sh`, `tools/image`); `bootimage` is gone. Framebuffer console `src/fb_console.rs` replaced the VGA text console (`tests/framebuffer.rs`, `tests/boot_framebuffer.rs`).
  - 100 Hz tick, measured at 499-500 ticks per 5 RTC seconds under QEMU (`tests/timer.rs`).
  - Aurora chrome in `src/aurora.rs`, checked by `tests/aurora.rs`: status bar "Larp OS" / "amnesisch: nein", hint bar `Enter` / `Backspace` / `help`, boot fade (`BOOT_FADE_MS` = 400).
  - The smoke test pixel-compares the screendump with the host rendering (`scripts/qemu_shell_smoke.py`); screenshot `docs/screenshots/aurora-shell.png` is a real screendump.
  - Controller-verified at head c3e468a: `cargo test` 80 `[ok]`, 0 failed; shell smoke test OK.
  - Not done / not verified: real hardware (M5), Tor (M3), browser (M4), amnesic live system (M2). The `Tab` and `Strg+K` hints are intentionally absent until M4 (no Tab completion or palette exists).

## Next
Milestone order from the spec (section 3); each milestone gets its own spec and plan first (brainstorming, spec, writing-plans). M1 and M2 are independent; M3 needs the existing network/TLS base (Phases 3-4); M4 needs M1 and M3; M5 needs M2 and M4.
1. **M2 Amnesic live system**: xHCI driver (mass storage at boot, keyboard), whole image in RAM, wipe on unplug and by hotkey (order in spec section 5). Acceptance: QEMU `device_del` triggers the wipe; a memory dump shows user and key memory zero afterwards; the measured wipe duration is documented (replaces the **[assumed]** "a few seconds"). Entry criterion: the `serial-console` mirror is OFF by default in the amnesic image (it copies everything typed and shown to COM1); since the smoke test reads its expected text from that mirror, this needs a separate test/smoke build profile that switches it on.
2. **M3 Tor**: first a spike with an abort criterion (Arti bootstrap against a local test Tor network, from ring 3; proposed details: chutney as test network, own runtime, sockets and time adapter); if it fails, a minimal client is evaluated in its own spec. Acceptance: packet capture shows only traffic to guards/bridges; a process without the Tor endpoint cannot open a socket; time deviation against the consensus blocks connection setup.
3. **M4 Terminal browser**: HTML to text in reader layout, link hints, process per tab, no JavaScript. Acceptance: host tests with broken and hostile HTML; open page, follow link, go back, end to end over Tor; command palette (`Strg+K`) and address bar (`Strg+L`).
4. **M5 Real hardware**: UEFI boot, real NIC, xHCI on real chipsets (proposed details: target device list, e1000e/RTL8168). Entry criterion: real-hardware images are built without the `serial-console` mirror (OFF by default; only the test/smoke profile turns it on, see M2). Acceptance: boot and browse on at least one real device.
5. **M6 Hardening**: verified boot, WLAN, external audit; spec only after M5.

Older items, still valid and not superseded:
1. Console/keyboard as real **service processes**; **revocation** of delegated handles.
2. Phase 5 (secrets, optional encrypted storage design) and Phase 6 (text browser, which reuses `https::get`).
3. Network hardening: per-program grants, IPv6, DHCP only on explicit request, advisory scan in CI.

## Stage C — networking (blocked on multi-process isolation and capability handles)
- PCI enumeration; one emulated NIC (e.g. virtio-net or e1000/RTL8139 under QEMU), interface down until authorized.
- Candidate stack: `smoltcp` (no_std; evaluate license/unsafe/features). DNS and TCP only through the authorization gate.
- TLS via an audited `no_std` implementation (e.g. `rustls` with a suitable crypto provider; evaluate feasibility). Certificate validation and trust store design before any `fetch`.
- Commands (only when real): `net status`, `net devices`, `net request host:port`, `net permissions`, `net revoke host:port`.
- Acceptance for `fetch https://example.com`: works end-to-end on the OS under QEMU user networking; fails closed on denied auth and bad certificates (tests for each).

## Later
- Secret-handling type with zeroization; RAM-only enforcement design; optional encrypted storage (AEAD + KDF, explicit consent).
- Text browser as an unprivileged process: HTTPS only, no JS/cookies/history by default, numbered links, `open N`/`back`, redirect checks.
- Verified boot chain (UEFI boot under QEMU/OVMF is done since M1; real hardware is M5, verified boot M6).
