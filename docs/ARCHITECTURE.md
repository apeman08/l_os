# Architecture

Status legend: **[impl]** implemented and exercised, **[partial]** exists but incomplete, **[planned]** not started, **[assumed]** believed but unverified.

## 1. Current state (assessed 2026-10-12, updated for M2 on 2026-10-15)

Target: `x86_64-l_os.json` (bare metal x86_64, soft-float, no red zone, panic=abort). UEFI boot via the `bootloader` 0.11 crate (kernel side: `bootloader_api`; image builder `l_os_image` and cargo runner `l_os_run`: host crate `tools/image`, compiled by the repository's `build.rs` into `target/l_os-tools`; firmware OVMF in QEMU; no shell involved, so the same runner is meant for Linux, macOS and Windows, only Linux tested). The kernel is a static position-independent executable; the bootloader picks its base address. Requires nightly Rust (`build-std`, `json-target-spec`, `abi_x86_interrupt`); pinned in `rust-toolchain.toml`. Emulator: QEMU `qemu-system-x86_64`. Stable Rust cannot build this repository.

The smoke test reads both bars back from the screendump and compares every row, bars included, pixel-exactly with the host rendering. Real hardware: [assumed] to work; scrolling reads framebuffer memory back, which can be slow on real GPUs. |

| Shell | [impl] | A Rust program running in **ring 3** (`user/src/bin/shell.rs`), supervised and restarted by the kernel. | Physical frames, paging, heap | [impl] | Frame allocator with free list (frames are zeroed on alloc and free; bitmap detects double free and panics; only the first 4 GiB of RAM is tracked). `OffsetPageTable`, 4 MiB heap at `0x4444_4444_0000` (`linked_list_allocator`, `src/allocator.rs` `HEAP_SIZE`). Wipe: the window's table frames are allocator frames (zeroed in stage 7), the BARs are not RAM; the window is used only until stage 3 (DMA stop). PCI BARs: 64-bit decoding and size probing in `l_core::pci_bar`, measured by `pci::bar_size` with decoding off and command/BAR restored on every path. |
| Processes (ring 3) | [impl, limited] | Up to 8 processes, each with its own address space (private user L4 slot, kernel mappings shared as supervisor-only), own 64 KiB kernel stack, preemptive round-robin on the PIT tick (time slice = 1 tick = 10 ms at 100 Hz since the change from 18.2 Hz, where it was ~55 ms; `sched::on_tick` yields on every tick that interrupted user code when another process is ready; `sched::wake_net` is called from the timer interrupt (the virtio IRQ handlers would call it too, but IRQ 9/10/11 stay masked) and makes network waiters (BlockedNet) Ready again on every tick, 100 times per second, so they poll the stack again), CPU-tick budgets, 32 KiB stack with an unmapped guard page, memory fully reclaimed on exit. Programs: validated static ELF executables built from `user/` (W^X enforced per segment) or raw machine code for the hand-assembled tests. `spawn`/`wait` from user space; idle in `hlt` while everything waits for the keyboard. |
| Syscalls | [impl, limited] | `int 0x80`: `exit write net_check yield close send recv spawn wait read_key sysinfo random net_connect sock_send sock_recv netctl`. Every user pointer is validated against the calling process's page tables; copies run in a SMAP window. |

## 2. Testing layers (be precise about what each proves)

- **In-kernel tests** (`cargo test`): the test binary is a kernel image booted in QEMU; results are reported over serial and `isa-debug-exit`. Kernel tests run through the UEFI runner (`l_os_run` from `tools/image`; not `bootimage`): each test binary is turned into a UEFI image and booted in QEMU with OVMF. Unit tests for the shell parser, line editor, scancode queue, and tick math run here.
- **QEMU smoke test** (`scripts/qemu_shell_smoke.py`): boots the real `l_os` image, types through the emulated PS/2 keyboard via the QEMU monitor, reads the console from the serial mirror and asserts on text, and compares a QEMU `screendump` of the framebuffer console pixel-exactly with the same lines rendered on the host by `l_core::render` (`crates/l_core/examples/render_text.rs`, which also draws the status and hint bars with the `l_core` widgets); check `shell_screen_has_status_and_at_most_three_hints` reads the first and last screen rows back as text by matching each cell against the font. A second screendump checks a screen that output has overflowed: the prompt is on the last text row above the hint bar. Exercises ISR → queue → decoder → editor → parser → console → framebuffer. The screenshot `docs/screenshots/aurora-shell.png` is a real QEMU screendump taken by this script (`--screenshot`), not a mock-up; it shows the uptime-dependent shell output of that run, so it changes whenever it is regenerated.
- **QEMU wipe acceptance** (`scripts/qemu_wipe_test.py`, M2): builds `cargo build --features wipe-test` (no mirror), boots the image from a read-only `usb-storage` stick on `qemu-xhci` (`--boot usb`, default; `--boot ide` keeps the stick attached and boots from IDE), types a random sentinel over PS/2, triggers the wipe (`--trigger hotkey`: QMP `send-key ctrl alt backspace`; `--trigger unplug`: QMP `device_del stick0`) and inspects a `dump-guest-memory` ELF core, a `screendump` and the serial log. Checks: `unplug_triggers_wipe` (unplug only), `wipe_report_present`, `poweroff_not_reset`, `key_slot_zero_after_wipe`, `usable_ram_zero_after_wipe`, `sentinel_absent_from_dump`, `screen_black_after_wipe`, `serial_log_has_no_sentinel`; positive controls before the trigger (sentinel in a pre-trigger dump, key slot non-zero, screen not black) make an absent sentinel meaningful. `--mem 256M` (default), `--measure 256M,1G,4G` prints the duration table. Proves the wipe in QEMU/TCG, not on hardware.
- **QEMU USB smoke** (`scripts/qemu_usb_smoke.py`, M2): `--features serial-console` build, IDE boot with the same image as read-only `usb-storage` plus `usb-kbd`; checks `usb_keyboard_types_into_shell`, `stick_read_count_constant_after_seal`, `keyboard_unplug_does_not_wipe`.
- **Cargo features** for tests (never default; `Cargo.toml`): `serial-console` (console mirror, smoke scripts, `cargo run-serial`), `wipe-test` (key slot 0 filled from RDRAND at boot, physical ranges and `WIPE-REPORT` on COM1; no change to wipe logic), `test-hooks` (`wipe::trigger` only counts; such a build never shows "amnesisch: ja"; used by `cargo test --features test-hooks --test usb_wipe_hooks`), `net-tests` (`scripts/net_tests.sh`). In-kernel `cfg(test)` builds also only count triggers. The USB kernel tests (`usb_*`) get `qemu-xhci`, the image as `usb-storage` and `usb-kbd` from the runner (`tools/image`, `usb_test_args`).
- **Host-side tests** (`scripts/host_tests.sh`): the `l_core` crate (`#![forbid(unsafe_code)]`: shell parser/editor, frame cursor, `NetPolicy`, capabilities, syscall ABI helpers, the M1 modules `cell`, `font`, `theme` (contrast tests), `render` (pinned by a golden hash), `widgets`, `anim`, and the M2 modules `wipe`, `memrange`, `zeroize`, `wipetime`, `hotkey`, `acpi`, `xhci_ring`, `xhci_ctx`, `usb_desc`, `usb_hid`, `usb_msc`, `bootmark`, `pci_bar`, with hostile-input tests for the parsers, e.g. `usb_desc::fuzz_never_panics`, `usb_hid::fuzz_any_report_never_panics_and_stream_is_well_formed`, `acpi::find_table_hostile_lengths_do_not_panic`, `pci_bar::size_from_probe_hostile_inputs`). The same script runs the unit tests of `tools/image` (cargo runner logic: test-binary detection, QEMU command line, exit-code mapping, timeout, QEMU and firmware discovery, Windows/macOS paths as data only). These run on the host, not in the kernel, so they prove the logic only, not that the kernel uses it correctly.
- **Kernel integration tests** (`tests/*.rs`: 34 files, `ls tests/*.rs | wc -l`; a full `cargo test` run at head f835d02 on 2026-10-15 gave 141 `[ok]` results, 0 failed, exit code 0, together with the in-crate unit tests; `tests/usb_wipe_hooks.rs` needs `--features test-hooks` and the `net-tests` files need `scripts/net_tests.sh`, so neither is part of that count). M2 added `acpi`, `boot_id`, `usb_xhci`, `usb_storage`, `usb_keyboard`, `usb_wipe_hooks` and `wipe_plan`. exceptions through the real IDT, heap/paging/frame reuse and double free, SMEP/SMAP violations (each with a passing control case), and ring-3 suites: `usermode` (kernel-memory isolation, privileged instructions, pointer validation, policy outcomes), `processes` (separate address spaces, preemption, crash containment, no frame leaks, table-driven pointer probe) `capabilities` (forged/closed handles, delegation, attenuation, deadlock cleanup) and `userland` (Rust ELF programs: W^X of the loaded image, corrupt-image rejection, spawn/wait limits, keyboard handle). Selected tests were checked by mutation (breaking the protection makes the test fail).

## 3. Kernel architecture decision (provisional)

Options considered:

| | Minimal monolithic | Microkernel |
|---|---|---|
| Trusted code | Larger: drivers/stack/FS in ring 0 | Smaller: scheduler, memory, IPC, capabilities |
| Isolation of faulty/hostile drivers | None | Strong (separate address spaces) |
| Performance | Best | IPC cost; fine for a terminal OS |
| Implementation cost | Lowest | High: needs user mode, address spaces, IPC *before* any service |
| Fit with capability model | Possible but easy to bypass in-kernel | Natural: capabilities are the IPC authority |

**Decision:** target a capability-based microkernel design, but build in stages so the project keeps working:

1. Kernel owns memory, interrupts, timer, and (temporarily) the console/keyboard. **Done.**
2. Introduce user mode, address spaces, syscalls, and kernel-enforced capability handles. **Done** for hand-assembled programs: separate address spaces, handles, IPC.
3. Move services (shell, network, filesystem, browser) out of the kernel as unprivileged processes holding only the capabilities they were given. **Started**: the shell now runs in ring 3 with a user-space build pipeline and dynamic spawn; network, storage and the console/keyboard "services" are still kernel objects, not processes.

Until step 2 is complete, isolation claims are limited to what `tests/usermode.rs` demonstrates. The shell and every service still run in ring 0, so a "policy" consulted only from ring-0 code remains advisory; only checks on the syscall path are a boundary. This ordering is a judgment call and should be revisited if user-mode bring-up proves disproportionately costly.

## 5. Font

`crates/l_core/src/font.rs` embeds an 8x16 bitmap font for the framebuffer terminal. The glyphs come from Terminus Font 4.49.1 (`ter-u16n.bdf`, https://terminus-font.sourceforge.net/), copyright (C) 2020 Dimitar Toshkov Zhekov, licensed under the SIL Open Font License 1.1. The licence text is in `crates/l_core/LICENSE-font`. The glyph table `crates/l_core/src/font_data.rs` is generated from the BDF by `scripts/gen_font.py` and must not be edited by hand. It covers ASCII, Latin-1, box drawing, block elements and a few symbols, sorted by codepoint; any other codepoint renders as a hollow-box replacement glyph. Terminus lacks some dashed box-drawing variants and a few others (U+2504-2507, U+254C-254F, U+2594-2595; checked against the codepoints in `font_data.rs`: every other codepoint in U+2500-259F is present); these are not covered and fall back to the replacement glyph. The replacement glyph itself is hand-drawn (not from Terminus).
