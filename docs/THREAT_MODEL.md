# Threat model (initial, for the current development stage)

This describes goals and what is **actually** defended today: the table "Current protections vs. gaps" below says, row by row, what is enforced and which test or script shows it (all under QEMU only). Ring-3 processes are isolated from each other and from the kernel, but the kernel and every driver run in ring 0, so any kernel bug defeats everything listed here. Do not treat any statement here as a guarantee about future behavior.

## Assets
Typed input and console contents; network destinations and fetched page content (`fetch`, TLS in ring 3); key material in RAM (TLS session keys in the `fetch` process, the kernel's key slots in `src/secrets.rs`); everything else the live session leaves in RAM (the target of the M2 amnesic wipe); (future) passwords and persistent volumes; kernel integrity.

## Adversaries (in scope as design targets)
1. **Remote network attacker / malicious site**: networking exists (virtio-net under QEMU, default deny, TLS 1.3 client in ring 3), so this adversary is real today.
2. **Malicious or buggy application/service**: ring-3 programs exist (built-in programs started by the shell, each in its own address space with capability handles).
3. **Passive observer of traffic** (DNS and connection metadata count).
4. **Offline attacker with a stolen powered-off device** (relevant once optional storage exists).
5. **Local physical attacker with a running device** (cold boot, DMA, firmware): *out of scope to fully defend*; documented as residual risk. Since M2 partly mitigated: pulling the boot stick, the emergency hotkey, loss of the USB controller and a kernel panic wipe RAM and power off (section "Amnesic wipe"); a plain power cut, DMA and firmware attacks are not covered.

## Out of scope / non-goals for now
Hardware bugs (speculative execution, Rowhammer), malicious firmware/BIOS/SMM, and a compromised build toolchain. Secure Boot is not implemented, so a modified boot image is undetectable.

## Current protections vs. gaps

| Property | Today | Truth |
|---|---|---|
| Network denied by default | **Enforced**: `NetPolicy` is checked in `net::connect` before DNS, before the NIC is initialized, and on every send/receive; revoke/expiry reset open connections. Default is no grants. | Verified in QEMU: 10 refusal tests and an empty QEMU packet capture for the never-authorized run; functional run produces traffic (so the capture works). The kernel network stack and driver are in the TCB (ring 0), DMA is not isolated (no IOMMU). Only the emulated virtio-net is supported. |
| RAM-only | No write path to any disk exists (no write command in the code). The only storage access is the USB boot stick: at boot the kernel reads LBA 0 (plus TEST UNIT READY / READ CAPACITY) to identify it, then seals the mass-storage path for good (`tests/usb_storage.rs::reads_refused_after_seal`, `z_restart_after_seal_skips_storage`; check `stick_read_count_constant_after_seal` in `scripts/qemu_usb_smoke.py`). | No claim about forensic traces beyond the wipe below: firmware, device-internal buffers and emulator disk images are outside our control. The whole image is in RAM because the bootloader loads it there (spec M2 §6); the kernel does not check that the RAM copy equals the stick (no verified boot, M6). |
| Amnesic wipe (M2) | **Enforced under QEMU**: removal of the boot stick, the emergency hotkey, loss of the xHCI controller or a kernel panic zeroes key slots, user frames, all allocated and all other `Usable` frames and the kernel's writable data, then powers off (section "Amnesic wipe" below). | Accepted by memory dump in QEMU/TCG only (`scripts/qemu_wipe_test.py`); real hardware is M5. Shows "amnesisch: ja" only when the conditions of spec E7 hold. |
| Telemetry | None in code | Source-auditable; the project is small. |
| Memory safety | Rust; `unsafe` limited to hardware access (port I/O, MMIO through the uncached window `src/mmio.rs`, xHCI/virtio DMA rings and buffers in `src/xhci.rs`/`src/virtio_net.rs`), page-table edits, asm entry/exit, the wipe's stack switch and final zeroing `asm!` (`src/wipe.rs`), user-pointer copies, heap init | Kernel bugs in `unsafe` or logic remain possible. `l_core` forbids `unsafe`. DMA memory is shared with devices and not isolated (no IOMMU). |
| User/kernel and process/process isolation | **Demonstrated** for up to 8 hand-assembled ring-3 processes: separate address spaces (same virtual address, different contents), no access to kernel pages, no privileged instructions, kernel pointers rejected in syscalls, runaway processes preempted and killed, crashes contained, memory reclaimed. SMEP/SMAP enabled when the CPU offers them. | Single CPU only. SMEP/SMAP absent on QEMU's default CPU model. Kernel mappings are shared by all processes (copied L4 entries; new kernel L4 entries created after a process exists are not visible to it). No guard pages under kernel stacks. No fuzzing; side channels (Spectre/Meltdown class) not addressed. |
| Capabilities | Per-process handle tables; syscalls resolve a handle first (kind and right checked); delegation needs `GRANT` and can only narrow rights; stale/forged/closed handles rejected | No revocation of delegated handles; no capability for devices/memory yet; endpoint queues are unauthenticated beyond the handle; a malicious holder of `GRANT` can pass on what it has (by design, attenuated). |
| Input hardening | Shell accepts printable ASCII only, bounded 128 bytes; console writes from user are filtered to printable ASCII | Prevents screen-control injection. |
| Console output on COM1 | With the cargo feature `serial-console` (off by default; enabled by `cargo run-serial` and the smoke scripts) every console write, including everything typed and shown, is also written to the serial port COM1; panic messages always are | Anyone who can read COM1 (the host, a serial cable, a VM log file) can record the console. The default build keeps normal console output off COM1 (default off; smoke builds opt in via the cargo feature; real-hardware images remain an M5 entry criterion, `docs/ROADMAP.md`). |
| The shell | Runs in **ring 3**, holds console (write+grant), keyboard, system-info (read) and a spawner limited to four built-in programs; a crash of the shell is contained and it is restarted | The shell can start the demo programs and pass them its console; it cannot touch memory, devices or other processes. Typed input is still restricted to printable ASCII; console writes from any holder of a console handle may use backspace/clear (full control of the text screen). |
| Exception handling | ring 3 faults kill the process; ring 0 faults, #NMI and #MC panic (`src/interrupts.rs`); **a panic outside a wipe starts the wipe** (`Trigger::Panic`, `src/main.rs`; `scripts/qemu_wipe_test.py --trigger panic`, check `panic_triggers_wipe`) | Fail-closed, no recovery for kernel faults: the machine is wiped and powered off. Without an armed wipe plan the panic wipe is the degraded one (no RAM zeroing). Virtualization/CET/VMM exceptions have no handler (they would double fault, which also panics). |

Known weaknesses specific to the process model: budgets are counted in PIT ticks (100 Hz, measured against the RTC only under QEMU); a process killed inside a syscall or ISR is abandoned together with its kernel stack, which is sound only if no lock is held at those points (tested, not proved); a process can fill its own handle table or endpoint queues but not others'; there are at most 8 endpoints per run; all drivers still run in ring 0, including the xHCI driver, which parses descriptors, HID reports and SCSI replies from any USB device plugged in at boot (parsers host-fuzzed: `usb_desc::fuzz_never_panics`, `usb_hid::fuzz_any_report_never_panics_and_stream_is_well_formed`, `xhci_ring::decode_never_panics_on_arbitrary_words`).

Loader-specific: ELF images are embedded in the kernel and validated by `l_core::elf` (window, alignment, overlap, W^X, entry point, file bounds). They are trusted code from our own build, but the parser treats them as untrusted; `build.rs` runs a nested cargo build with a scrubbed environment, so the build host's toolchain and network (crates.io, locked by `user/Cargo.lock`) are part of the trusted computing base for the user programs.

Firmware and the NIC: the "nothing is sent" check in QEMU (`scripts/net_tests.sh`) depends on the boot disk having `bootindex=0`, so that OVMF connects only the disk and leaves the NIC alone; without it, OVMF's own network stack sent IPv6 frames (MLD report, neighbour solicitation carrying the MAC address) before the kernel started. Real UEFI firmware may likewise send frames (e.g. MLD/NS with the MAC, PXE/DHCP) before the kernel runs; the kernel cannot prevent that.

Network and TLS specifics: a connection needs a `NetClient` handle and an exact `host:port` grant (names also need the DNS resolver granted); only the shell can create grants, after a typed confirmation. TLS is TLS 1.3 only, client only, no fallback; certificate validity depends on an unauthenticated RTC; no revocation checking; the production trust store is the embedded Mozilla root list. The user-space TLS and HTTP code parses attacker-controlled data in ring 3 (a crash kills only `fetch`). A compromised shell is a compromised trusted path: it can grant anything.

## Limits (not defended; from the Zukunftsplan spec section 4)
These are stated as limits of the design, not as tested behaviour; none of them has a test.
- **Manipulated firmware** (UEFI/BIOS, SMM) is not covered (see Out of scope above). Secure Boot / verified boot is not implemented (planned M6).
- **Hardware keyloggers** and other hardware between keyboard and machine are not covered.
- **DMA attacks**: there is no IOMMU, so devices (NIC, USB, anything on the bus) are trusted; the same holds for the NIC once a real one is supported.
- **Cold boot**: RAM contents are readable after power-off for a short time. Since M2 the wipe (section "Amnesic wipe" below) zeroes RAM before powering off when the boot stick is pulled, the emergency hotkey is pressed, the xHCI controller is lost or the kernel panics; it only mitigates cold boot. A plain power cut or a shutdown by other means does not wipe. The wipe takes time: measured under QEMU 8.2.2 with **TCG** (no KVM; host time from the QMP command to QEMU's `SHUTDOWN` event, `scripts/qemu_wipe_test.py --measure 256M,1G,4G`, `docs/superpowers/notes/2026-10-14-m2-wipe-measurements.md`): 256 MiB hotkey 1.20 s / unplug 1.11 s, 1 GiB 3.14 / 3.94 s, 4 GiB 6.85 / 7.01 s; about ±20 % run to run within that session (seen at 256 MiB), single runs at 1 GiB and 4 GiB; a re-run at 256 MiB on 2026-10-15 on the same nominal host took 0.58 s (hotkey) and 0.35 s (unplug), so the values depend strongly on host load. Keys were zeroed after 5-8 ms and user-process frames after 12-23 ms (guest TSC times from the `WIPE-REPORT` line); the rest is zeroing free memory. These numbers say nothing about real hardware (M5). An attacker who cuts power during the wipe finds the not-yet-zeroed part.
- **Tor** (planned M3, not present today; the system has no Tor code): Tor is not a guarantee against fingerprinting or global observers, and the design does not claim otherwise.
- The status bar shows "amnesisch: ja" only when the boot stick is identified and sealed **and its removal watch is armed**, the wipe plan is armed, the serial mirror is off and the build has no `test-hooks` (`src/wipe.rs` `amnesia`, `l_core::wipe::Amnesia`; `tests/usb_storage.rs::amnesia_label_reflects_stick_and_mirror` (sealed but unwatched stick ⇒ "nein"), `tests/usb_wipe_hooks.rs::arming_required_before_any_trigger` / `stick_present_level_poll_does_not_trigger` (the stick input turns true on arming), host `wipe::amnesia_label_ja_only_when_all_true`); otherwise "amnesisch: nein", with the reason in `security` (an unwatched stick reads "kein Boot-Stick").
Already covered above: console output is mirrored to COM1 only with feature `serial-console` (off by default) and OVMF/firmware may emit frames before the kernel runs.

## Amnesic wipe (M2)
Spec `docs/superpowers/specs/2026-10-13-m2-amnesisch-design.md` §7-§8. Everything here is shown under QEMU/OVMF (TCG) only.

**Triggers** (first one wins, `l_core::wipe` host tests `first_trigger_wins`, `trigger_names_are_distinct_report_tokens_and_codes_roundtrip`; all run the same sequence):
- `Hotkey`: `Strg+Alt+Rücktaste` (left or right Ctrl, Alt or AltGr), recognized in the kernel, not in the shell, on PS/2 in the keyboard ISR and on the USB keyboard in the HID path (one shared detector; host `hotkey::*`, `usb_hid::ctrl_alt_backspace_via_hid_fires_hotkey_detector`). End to end: `scripts/qemu_wipe_test.py --trigger hotkey` (PS/2). The USB-keyboard hotkey wipe was tried by hand only, not by a CI check.
- `StickRemoved`: the stick watch reads USBSTS and the boot stick's PORTSC lock-free on every timer tick (100 Hz polling, no interrupts) and triggers at the first reading with CCS=0 **or** CSC=1 on the stick's port (also when CCS=1 again, i.e. a quick unplug/replug counts as removal). End to end: `scripts/qemu_wipe_test.py --trigger unplug` (QMP `device_del`, check `unplug_triggers_wipe`); host `xhci_ctx::watch_stick_disconnect_is_stick_removed_at_first_reading`.
- `ControllerLost` (fail-closed: whoever cannot watch the stick wipes): USBSTS with HCE, HSE or HCH set (HCH means the controller stopped after the watch was armed) or all-ones reads. Checked only with simulated all-ones reads, `tests/usb_wipe_hooks.rs::controller_gone_triggers_wipe_hook`, and host `xhci_ctx::watch_controller_loss_wins_and_is_fail_closed`; QEMU cannot remove the controller.
- `Panic` (fail-closed): a kernel panic outside a wipe. Syscalls and ISRs run with interrupts off and a panicked kernel used to halt there, deaf to the stick watch and the hotkey while RAM was intact; now the panic handler (`src/main.rs`) prints the message (COM1 and screen) and then calls `wipe::trigger(Trigger::Panic)`, which is lock-free and never returns. With an armed plan this is the full wipe; without one the degraded wipe below (the decision: fail-closed in both cases, so a panic on a system with "amnesisch: nein" also blanks the screen and powers off; the panic text survives only on COM1). Not in `cfg(test)` or `test-hooks` builds, whose test kernels keep their own panic handlers. End to end: `scripts/qemu_wipe_test.py --trigger panic` (F12 makes a `wipe-test` build panic in the keyboard ISR; checks `panic_triggers_wipe` and all dump checks).
- Not triggers: unplugging the USB keyboard (`keyboard_unplug_does_not_wipe` in `scripts/qemu_usb_smoke.py`), new devices on other ports (counted, ignored).

**Sequence** (`l_core::wipe::ORDER`, host `stage_order_matches_spec_section_5`): input locked (`cli`, PIC lines and NMI masked), screen black (`screen_black_after_wipe`), DMA stopped, stack switched to the "island", then zeroed in this order: key slots (`key_slot_zero_after_wipe`), user-process frames, every allocated frame (heap with console grid and process kernel stacks, page tables, DMA rings), every other frame of every `Usable` region including above 4 GiB (`usable_ram_zero_after_wipe`; the 4 GiB measurement run covered a region ending at 5 GiB), the kernel's writable segments (`.data`/`.bss`) and boot stack; finally the island itself is zeroed by one `asm!` block without stack, `wbinvd`, ACPI S5 (`poweroff_not_reset`), with reset and `cli; hlt` as fallbacks. The typed sentinel is found nowhere in the memory dump afterwards (`sentinel_absent_from_dump`) nor in the serial log (`serial_log_has_no_sentinel`). Zeroing uses `rep stos` in the kernel; the `l_core::zeroize` helpers (not used by the wipe) rely on `black_box`, which is best effort only.

**DMA stop**: before anything is zeroed the xHCI controller is halted (`USBCMD.RS=0`, bounded wait for HCH; `tests/usb_xhci.rs::halt_for_wipe_stops_controller`) and the bus-master bit of every enumerated PCI function is cleared (`src/wipe.rs::disable_bus_master_clears_bit2`), so that no device writes keystrokes or packets back into zeroed RAM. There is **no IOMMU**: a device that ignores the bus-master bit, or one that is not on an enumerated PCI function, is not stopped.

**Not zeroed** (spec §8.4): code and read-only data (`.text`, `.rodata` with the embedded programs and the font), RELRO, and the bootloader's copy of the kernel ELF (public, identical to the stick); the bootloader's page tables and boot info (addresses, no user data); UEFI/ACPI firmware regions; device-internal buffers and QEMU's own memory; CPU registers and caches beyond `wbinvd` (best effort).

**Windows and degraded cases** (none of these has a test of its own):
- *Stick pulled before detection* (spec E8): unplugging before the kernel has identified and sealed the stick does not wipe; the system then runs with "amnesisch: nein", and only the hotkey wipe is armed. No user state exists at that point (the shell starts after the stick check). A stick that is gone after identification but before the watch is armed is caught by the watch's first reading at arming. This replaces the Zukunftsplan §5 sentence "Ein Abziehen während des Boots führt zu Halt".
- *Detection latency*: the stick is polled once per timer tick (10 ms at 100 Hz) by design; the latency itself was not measured separately (the host times above include it).
- *Wipe without a plan* (arming failed, e.g. more than 64 `Usable` regions, a list overflow or a mapping check failure; status "amnesisch: nein"): the wipe still locks input, blanks the screen, stops DMA, zeroes the key slots and powers off, but does **not** zero RAM.
- *Panic during the wipe*: the panic handler jumps straight to the power-off/reset tail; RAM can be left partly unzeroed. After stage 9 the IDT is zero, so any exception is a triple fault (reset), with the same consequence. (A panic **outside** a wipe is a trigger, see above; it is no longer a gap.)
- *Panic before the wipe plan is armed* (early boot) or on a system without a plan: the degraded wipe runs (screen, DMA stop, key slots, power off or reset); on real hardware an early-boot panic therefore resets or powers off instead of halting with the message on screen.
- `total_us` in the `WIPE-REPORT` line ends at `KernelZeroed`, a lower bound; the host time includes the rest.
- On real hardware a spurious connect-status change or a SuperSpeed fallback on the stick's port would wipe (fail-closed; M5).

## Principles for upcoming work
- Enforcement lives in the kernel at a boundary untrusted code cannot bypass (syscalls/IPC capability checks), never in the shell.
- DNS is a network operation and needs the same authorization as TCP.
- TLS and crypto only via vetted `no_std` libraries; certificate validation must work before any HTTPS feature is exposed; no HTTP fallback.
- Secrets: dedicated zeroizing type, minimal copies; documented as best-effort (registers, caches, swap-like copies cannot be guaranteed cleared).
- Persistent storage: separate, opt-in, authenticated encryption, explicit consent; design before code.
